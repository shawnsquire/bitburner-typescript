# Darknet: swarm cracker, coordinator and dashboard

Design agreed 2026-09-19. Status: not yet implemented.

Game facts below are from the `bitburner-src` checkout at tag `v3.0.1`
(`~/documents/apps/games/bitburner`). Paths in citations are relative to that repo.

## Problem

Bitburner 3.0 added the Darknet: an 8-wide, up to 40-deep grid of password-protected
servers reached through `darkweb` (`src/DarkNet/Enums.ts`). The grid mutates every
`30 s / depth` (twice as often outside BN15): servers move, restart, vanish, and get
their hostnames recycled onto new servers with new passwords
(`src/DarkNet/controllers/NetworkMovement.ts`). Rewards are `.cache` files (programs,
stock access, shares, money, contracts), charisma XP, phishing income, six special
augmentations and The Red Pill from labyrinth mazes at the bottom of the net.

Everything is scriptable through `ns.dnet` (24 functions, `src/NetscriptFunctions/Darknet.ts`),
but with one hard constraint that shapes the whole tool: `authenticate`, `heartbleed`
and `memoryReallocation` require the **calling script's host** to be directly connected
to the target (`checkDarknetServer`, `src/DarkNet/effects/offlineServerHandling.ts:40-126`,
no backdoor bypass). A daemon on `home` can only reach `darkweb`. Cracking must be done by
scripts that live on darknet servers and spread outward.

Other facts that drive decisions:

- `probe` (0.2 GB) lists a host's darknet neighbours, shuffled. `getServerDetails` (0.1 GB)
  works at any distance and exposes `modelId`, `passwordHint`, `data`, `passwordLength`,
  `passwordFormat`, `difficulty`, `depth`, `requiredCharismaSkill`, `blockedRam`,
  `isOnline`, `isConnectedToCurrentServer`, `hasSession`. Neither reveals a server's column.
- `authenticate` returns only success or failure for ordinary servers. The per-model
  feedback (Mastermind counts, Higher/Lower, RMS deviation, ...) is written to the target's
  log as a JSON `PasswordResponse` and read back with `heartbleed`
  (`src/DarkNet/models/packetSniffing.ts:90-127`, `src/DarkNet/effects/authentication.ts`).
  `heartbleed` costs 1.5x auth time, needs charisma at or above the target's requirement,
  and permanently sets `DarknetState.hasUsedHeartbleed`, which forfeits the BN15 challenge
  achievement.
- Sessions are per PID and die with the script. A restart clears sessions and the backdoor
  and kills every script on the host, but keeps admin rights and the password (only a delete
  or a hostname recycle resets those). `connectToSession` (0.05 GB, synchronous, any distance)
  restores a session from a known password on any server that still has admin rights, so after
  a restart the vaulted password reconnects on the first call and the agent re-execs to revive
  the killed swarm process.
- `exec` onto a darknet server needs admin, a session, and adjacency or a backdoor flag
  (`src/NetscriptFunctions.ts:641-652`). `scp` needs admin and a session only. A stasis link
  sets the backdoor flag (`src/DarkNet/effects/effects.ts:222-243`), so stasis hosts are
  remotely exec-able anchors, but they count toward the instability formula:
  auth timeout chance `(backdoored - 2) * 0.03` capped at 0.5, auth time `1.07^surplus`
  over `max(adminMovableServers / 24, 2)` (`effects.ts:92-99`,
  `offlineServerHandling.ts:151-154`).
- Rows at multiples of 8 are air gaps. Crossing means riding a server that moves: a
  move keeps its scripts alive (only restart and delete kill them), natural moves land
  within +-3 rows of the server's difficulty, and an induced migration lands within
  `[difficulty - 2, difficulty + 4]` (`NetworkMovement.ts:230-260`, `effects.ts:245-262`).
  Air gaps and labyrinths only exist with full access (BN15 or SF15); otherwise the net
  is 5 deep (`src/DarkNet/effects/labyrinth.ts:485-497`).
- Unlock is `DarkscapeNavigator.exe`, $50m on the TOR router. `daemons/darkweb.ts` already
  buys every program `getDarkwebPrograms` lists, so no new unlock code is needed.

## Decisions

1. **Whole feature in one design**, five subsystems, built in the order of the sections
   below. Sections 1 to 4 are the minimum that does anything.
2. **Hybrid brains.** Agents on darknet servers crack and replicate on their own; the home
   coordinator owns the map, the password vault, budgets and policy. Rejected:
   hub-and-spoke (home decides every attempt; a port round trip per attempt is too slow
   against mutation at depth) and no coordinator (nothing durable, no global budgets).
3. **Heartbleed is a config key, default on.** Off keeps the BN15 achievement alive at the
   cost of the feedback solvers.
4. **Charisma is requested, not seized.** The daemon publishes a charisma target; the
   advisor turns it into a recommendation. Nothing touches focus directly.
5. **Deferred**: terminal backdoors (stasis anchors already give remote seeding, and the
   instability tax is steep), stock promotion (the stocks daemon does not model
   volatility; extend `sim/stocks/` first), automatic storms (manual by default).

## Section 1: components and files

Ports, in `types/ports.ts`:

| Port | Name | Direction | Content |
|---|---|---|---|
| 34 | `STATUS_PORTS.darknet` | coordinator -> dashboard, advisor | `DarknetStatus`, one value |
| 35 | `DARKNET_CONTROL_PORT` | dashboard -> coordinator | JSON commands, FIFO |
| 36 | `DARKNET_POLICY_PORT` | coordinator -> agents | one JSON `Policy`, replaced each tick, read with peek |
| 37 | `DARKNET_REPORT_PORT` | agents, workers -> coordinator | JSON `Report` events, FIFO |

Home side:

- `daemons/darknet.ts`: the coordinator. Not tiered; every call it makes is cheap
  (about 4.5 GB total: base, `getServerDetails`, `probe`, `scp`, `exec`,
  `connectToSession`, the zero-cost getters, `getResetInfo`). Reads `/config/darknet.txt`.
- `controllers/darknet.ts`: pure functions `applyReport`, `refreshFromDetails`,
  `computePolicy`, `charismaNeed`, `selectCarriers`, `stasisPriority`. Unit tested.
- `lib/darknet/vault.ts`: read and write `/data/darknet-vault.json`. Zero ns.
- `lib/darknet/protocol.ts`: `Policy`, `Report`, `Cell` types and `AGENT_VERSION`. Zero ns.
- `lib/darknet/leaks.ts`: log-line parser. Zero ns.
- `lib/darknet/solvers/<model>.ts` and `index.ts`: one pure solver per `modelId`.

Darknet side, each a small script with a pinned `ns.ramOverride` literal:

| Script | Role | Approx RAM |
|---|---|---|
| `workers/dnet-agent.js` | probe, crack, replicate, launch local workers, report | 5 GB |
| `workers/dnet-harvest.js` | memory reallocation, cache opening, contract discovery on its host | 4.7 GB |
| `workers/dnet-phish.js` | phishing loop, threads from policy | 3.7 GB |
| `workers/dnet-lab.js` | labyrinth walker, runs adjacent to the current lab | 2.1 GB |
| `workers/dnet-stasis.js` | one-shot: set or clear a stasis link on its own host | 13.6 GB |
| `workers/dnet-charge.js` | charge a migration on a neighbour until it moves | 5.6 GB |

RAM figures are estimates; each script's literal is fixed with `npm run ram` when written
(the agent also pays 1 GB for `run`).

There is no bundler (`build` is plain `tsc`) and the game resolves imports on the host
that runs the script, so replication must copy the import closure, not just the entry
files. `lib/darknet/protocol.ts` exports `DNET_BUNDLE`, the full list of worker entry
files plus every `/lib/darknet/*` module they import, and a vitest test walks the import
graph from each worker and fails if a file is missing from the list. Worker scripts must
import only from `lib/darknet/` and `types/`, never from `lib/utils` or other home-side
modules, to keep the closure small.

Dashboard: `views/dashboard/tools/darknet.tsx`, Servers group, `ToolName` `darknet`,
`DAEMON_PATHS.darknet = "daemons/darknet.js"`, state-store peek and pid wiring like darkweb.

Docs: `docs/systems/darknet.md`, an index line in `docs/README.md`, and
`tools/test-darknet.mjs` wired into `npm test`.

## Section 2: the agent loop

Identity: hostnames are mangled and 3 percent are recycled onto new servers. Every
report and vault entry carries a fingerprint `{ difficulty, modelId, passwordLength }`.
A vault entry whose fingerprint no longer matches live details is dropped.

Loop on host `H`, period `agentIntervalMs` (default 2000):

1. Peek the policy port. If `policy.version !== AGENT_VERSION`, exit (the coordinator
   re-execs the new bundle). If `policy.pause`, sleep and continue. `policy.charisma` is
   the player's current charisma, so agents never pay for `getPlayer`.
2. `probe()`. For each neighbour `N`: `getServerDetails(N)`, report `seen`.
3. If `policy.vault[N]` exists with a matching fingerprint, `connectToSession(N, pw)`.
   A restart keeps admin rights and the password (it clears only sessions, the backdoor and
   running scripts), so this succeeds on the first call; the agent then re-execs itself onto
   `N` (with `preventDuplicates`) to revive the process the restart killed. `authenticate(N, pw)`
   is a fallback only if `connectToSession` returns `AuthFailure`; only an `AuthFailure` from
   that fallback reports `stale` (the password genuinely stopped working); `RequestTimeOut` and
   `ServiceUnavailable` do not. Because `getServerDetails().hasSession` short-circuits an
   already-connected neighbour, this restore-and-revive runs once per neighbour and again after
   each of its restarts, not every tick.
4. Otherwise run the solver for `details.modelId`. Blind solvers yield a candidate list
   from `passwordHint` and `data`. Feedback solvers yield one attempt; after a failed
   `authenticate` the agent calls `heartbleed(N, { peek: true, logsToCapture: 10 })` only
   when `policy.heartbleed` is true and `policy.charisma` meets `requiredCharismaSkill`.
   Heartbleed returns log messages without their PID, so the agent finds its record by
   `passwordAttempted` equal to what it just sent (10 lines, because noise lines are
   inserted before every attempt and other agents may share the target) and feeds the
   `data` field to the solver. Every log line also goes through `lib/darknet/leaks.ts`.
5. On success, report `cracked { host, password, fingerprint }`, `scp` the bundle to `N`
   and `exec` the agent there with `preventDuplicates` if `N` has free RAM for it.
6. Launch local workers on `H` via `run` according to `policy.workers[H]`
   (`{ harvest, phishThreads, lab, stasis, charge }`). Home cannot `exec` onto ordinary darknet
   hosts, so this is the agent's job.
7. Per-server attempt cap `maxAttempts`, exponential backoff on `RequestTimeOut`, never
   retry on `ServiceUnavailable`. An agent with nothing crackable sleeps 10 s.
8. Reports are batched: one `tryWritePort` per agent per tick carrying an array of
   events. Ports hold 50 entries, and one entry per event would overflow with a few dozen
   agents. If the write fails the batch is kept and retried next tick, capped at 200
   events.

Charisma gate: a neighbour whose `requiredCharismaSkill` exceeds the player's charisma is
reported as `gap` and skipped for heartbleed.

Death is normal. Restarts and deletions kill agents silently; the vault lives on home
and the map is rebuilt from `seen` reports and the coordinator's own polling.

## Section 3: solvers

One pure state machine per model in `lib/darknet/solvers/<model>.ts`, keyed by the exact
`modelId` string (`src/DarkNet/Enums.ts:15-43`), with `next(state, details, feedback)`
returning `{ attempt, state }` or `{ giveUp }`. Blind solvers never need heartbleed.
Generators cited from `src/DarkNet/controllers/ServerGenerator.ts`.

Leak parser, applied to every heartbleed line regardless of model
(`packetSniffing.ts:155-192`): `Connecting to X:pw ...` (vault candidate for X),
`--pw--` (candidate for any host), `There's definitely a A and a B` (chars present),
`The characters A, B are in the right place`.

Testing: `tools/test-darknet.mjs` loads the game's `ServerGenerator.ts`,
`authentication.ts` and `dictionaryData.ts` from the checkout the way
`tools/test-contracts.mjs` does, generates N servers per model at difficulties
1, 4, 8, 18, 30, and drives each solver through `checkPassword` until success or its
cap. That is the acceptance test. Vitest units cover parsing edge cases.

## Section 4: the coordinator

Tick every 2 s:

1. Drain the report port until empty; each entry is an array of events. Apply every
   event with `applyReport`: `seen`, `cracked`,
   `stale`, `leak`, `gap`, `cache`, `ramfreed`, `contract`, `storm-seed`, `lab`, `error`.
2. `getServerDetails` for every known hostname. Offline hosts get a tombstone; a changed
   fingerprint resets the cell to unknown and drops its vault line.
3. `computePolicy` and write it to the policy port:
   `{ version, pause, heartbleed, charisma, vault, workers, stasisTargets,
   migrationTargets, labHost, labGrid }`.
4. Re-seed: if no agent is alive on `darkweb`, `scp` `DNET_BUNDLE` and `exec` there. Same
   for every stasis-linked host: `exec` reaches it through the backdoor flag, and stasis
   hosts are exempt from restart, move and delete (`isImmutable`,
   `NetworkMovement.ts:227-228`, checked by `restartServer` at `:301-304`), so their
   admin rights and vault password stay valid. `connectToSession` from home gives the
   coordinator its session first.
5. Forward `contract` events as `{ host, file }` to `CONTRACTS_CONTROL_PORT`; the
   contracts daemon cannot find darknet hosts itself because `scan` hides them.
6. Publish `DarknetStatus`; save the vault when it changed.

Vault: `/data/darknet-vault.json`, `hostname -> { password, fingerprint, seenAt }`,
plus `lastNodeReset` compared with `getResetInfo().lastNodeReset` to wipe on a new
BitNode.

Budgets:

- Stasis links, limit `getStasisLinkLimit()` (1 plus one each for Wings, Hammer, Staff).
  `auto`: deepest admin host adjacent to the current lab, then the deepest admin host
  below each crossed air gap, then a darkweb-adjacent host only if it has at least 20 GB
  so the 13.6 GB stasis worker fits beside the agent. A link moves only when its host
  goes offline or a candidate is two or more rows deeper.
  `manual`: targets from the control port.
- Heartbleed from config. Nothing exposes the game's flag, so status carries
  `heartbleedUsedThisNode`, set the first time the coordinator allowed one.
- Terminal backdoors: deferred (see Decisions).

Charisma need: the smallest `requiredCharismaSkill` above the player's that unblocks the
most frontier servers, or the current lab's threshold if lower. Published as
`{ target, unlocks, reason }`. The advisor gains a rule: recommend charisma training when
the target is within reach and fewer than 3 frontier servers are crackable.

Map: rows by depth, cells sorted by hostname, edges from probe reports. The API never
reveals a column, so the dashboard draws a depth ladder, not the game's grid.

## Section 5: harvest and grind

`workers/dnet-harvest.js` on host `H`, launched by the agent when
`policy.workers[H].harvest` (default: `getBlockedRam(H) > 0` or a `.cache` exists):

1. `memoryReallocation()` until `NoBlockRAM`. Threads sized to free RAM; each call frees
   `0.02 x 2 x 0.92^(difficulty+1) x threads x (1 + cha/100)` GB
   (`src/DarkNet/effects/ramblock.ts:71-82`). Clearing the block awards a cache and rolls
   the 15 percent storm seed (30-minute global cooldown).
2. `ls(H, ".cache")` and `openCache` each. Cost `difficulty + 1` karma
   (`src/DarkNet/effects/cacheFiles.ts:35-74`); skipped below `harvestKarmaFloor`.
   Report `cache { host, message }`.
3. `ls(H, ".cct")` and report `contract` for each. Phishing caches (`.d.cache`) place up
   to 3 contracts on the darknet host itself, 10-minute cooldown.
4. Report `storm-seed` if `STORM_SEED.exe` exists; never run it.
5. Exit when the block is empty and no caches remain.

`workers/dnet-phish.js` with `phishThreads` from policy (free RAM after agent and harvest,
divided by its own cost, capped by `phishMaxThreads`). One call sleeps
`max(10000 x 400 / (400 + cha), 200)` ms. Cache chance
`0.005 x crime_success x threads x (400 + cha)/400` behind a 3-minute global cooldown;
money chance `0.05 x crime_success x (200 + cha)/200`, paying
`500 x mults x (0.1 + 0.05 x depth) x threads x ...` (`src/DarkNet/effects/phishing.ts`).
Reports `phish { money, cache }` so status shows income per hour.

## Section 6: air gaps, stasis, storm

Idle without full access.

Stuck detection: every admin host at depth `8k - 1` or `8k - 2` has been probed and no
neighbour lies below row `8k` for `gapPatienceMs` (default 300000).

Riding across: carriers are admin hosts with difficulty in `[8k - 3, 8k - 1]`, whose
induced move range `[difficulty - 2, difficulty + 4]` reaches past the gap. They go in
`policy.migrationTargets`. Every agent adjacent to a carrier runs `dnet-charge.js` with
all free RAM. Charge per call is
`((cha + 500) / (difficulty x 200 + 1000)) x 0.01 x threads`, 6 s per call; five hosts
charging one carrier at a few threads each cross in minutes. The carrier's own agent
survives the move, probes at the new depth, and the swarm continues. Charging stops when
the carrier reports a depth past the gap.

Stasis: set and cleared by `dnet-stasis.js` on its own host, the only host
`setStasisLink` accepts. It needs 13.6 GB, so hosts of 16 GB with an agent resident
cannot hold a link; the priority rules above only pick hosts where it fits. Priority and modes as in section 4. The dashboard has a pin
toggle per cell that sends `{ action: "stasis", host, link }`.

Storm: `storm = manual` by default. `auto` fires only when stuck, no carrier exists, and
every stasis link is placed. Before any storm the coordinator sets `policy.pause` for
30 s. The storm deletes about 60 percent of movable servers, moves 60 percent of the
rest, restarts everything, then re-seeds 40 servers over 20 s
(`src/DarkNet/effects/webstorm.ts:41-70`). Stasis hosts are immune.

## Section 7: the labyrinth

Runs on the admin host at `labDepth - 1` named in `policy.labHost` (the stasis-linked one
if any). Launched only when the player's charisma meets the lab's threshold
(300, 600, 1500, 2500, 3000, 3500, 4000, 4000 by lab, `src/DarkNet/effects/labyrinth.ts:37-110`);
below it every move fails, so the gate is reported as a charisma need instead.

Walking: a move is `authenticate(lab, "north" | "east" | "south" | "west")`. Corridors
are odd cells, walls even, and a move jumps two cells. For lab servers the result carries
`data`, a 3x3 view with `@` at the new position, so each step costs one auth delay and
reveals the four neighbouring walls without `labreport`. The walker keeps an explored
grid and runs depth-first search biased toward the bottom-right corner, where the exit
sits unless `offsetStartAndEnd`. Every 20 moves in the bottom-right quadrant it calls
`labradar` once (7x7 view, `X` marks the exit when within 3 cells); a sighting switches
it to shortest-path over the known grid. Position is tracked per PID, so one walker does
the whole maze.

Persistence: the walker sends its explored grid home in `lab` reports every 25 moves.
A restarted walker starts at the entrance but receives `policy.labGrid`, so it replays
the known corridor instead of re-exploring.

Finishing: on success `data` holds the lab's real password and the lab gains admin with
one `the_great_work.cache` (three on the bonus lab). The lab has 128 GB. The agent next to
it calls `connectToSession(lab, password)`, `scp`s the harvest worker and `exec`s it;
`openCache` there awards the augmentation. Status reports `labCleared`; the vault stores
the lab password.

Progression: which lab is current depends on which reward augmentations the player holds,
and the net deepens to that lab's depth. The daemon publishes
`lab: { name, cha, cleared, augPending }`; the advisor suggests installing when a
great-work augmentation is queued. Installing augmentations prestiges the darknet's
volatile state but servers persist through `AllServers`.

## Section 8: dashboard, config, status, testing

`DarknetStatus` (port 34): `access` (`none` | `basic` | `full`), `heartbleedAllowed`,
`heartbleedUsedThisNode`, `counts { seen, admin, agents, frontier, offline }`,
`deepestAdmin`, `netDepth`, `instability` (from `getDarknetInstability`),
`stasis { used, limit, hosts }`, `charismaNeed`, `lab`,
`income { moneyPerHour, cachesOpened, contractsFound, augsAwarded }`,
`map { rows: Cell[][], edges: [string, string][] }` with
`Cell = { host, model, difficulty, cha, state }` and
`state` in `unknown | frontier | cracking | admin | agent | anchor | offline`,
plus `_publishedAt`.

Control port 35: `{ action: "set", key, value }`, `{ action: "stasis", host, link }`,
`{ action: "storm" }`, `{ action: "reseed" }`. The dashboard sends one `Command` action,
`darknet-control`, carrying the payload.

`/config/darknet.txt`:

| Key | Default | Meaning |
|---|---|---|
| `heartbleed` | `true` | allow heartbleed; `false` protects the BN15 achievement |
| `harvest` | `true` | run memory reallocation and cache opening |
| `phish` | `true` | run phishing on spare RAM |
| `phishMaxThreads` | `64` | per-host cap |
| `harvestKarmaFloor` | `-1e12` | stop opening caches below this karma |
| `stasisMode` | `auto` | `auto` or `manual` |
| `storm` | `manual` | `manual` or `auto` |
| `lab` | `true` | run the walker when charisma allows |
| `gapPatienceMs` | `300000` | stuck time before charging carriers |
| `agentIntervalMs` | `2000` | agent loop period |
| `maxAttempts` | `120` | per server per agent before backoff |

Dashboard tab in the Servers group. Overview card: agents alive, admin count, deepest
row, instability, next charisma gate. Detail panel: the depth ladder coloured by state
with a pin toggle per cell; a right column with stasis links, lab progress, income, the
storm button when a seed exists, and a config editor for the keys above.

Error handling: dnet calls return codes rather than throwing, except `openCache` and
non-darknet hostnames. Agents wrap each host in try/catch and report `error` with the
code; `ServiceUnavailable` is never retried, `RequestTimeOut` backs off,
`NotEnoughCharisma` is a gap. The coordinator ignores malformed reports. Without
`DarkscapeNavigator.exe` on home the daemon publishes `access: none` and sleeps 60 s.

Testing: vitest units for the controller (`applyReport`, `computePolicy`,
`charismaNeed`, `selectCarriers`, `stasisPriority`), the vault, the leak parser and each
solver's parsing; `tools/test-darknet.mjs` against the game's generators and checker,
added to `npm test`; the existing RAM invariant test covers each worker's pinned literal.

## Implementation order

1. Protocol types, ports, vault, blind solvers, the solver harness.
2. Agent and coordinator with seeding, replication and status. Dashboard card and ladder.
3. Feedback solvers and the leak parser.
4. Harvest and phish workers, contracts forwarding, income in status.
5. Stasis and charge workers, carriers, storm gate.
6. Labyrinth walker and the advisor rules.
7. `docs/systems/darknet.md` and the README index line, updated with each step.
